Make `elepha init` a staged onboarding flow. Capture tools, project roots and search mode are only staged until one final review, which names the exact roots to approve or pause and explains filtered memory, physical scope, the fixed 5,000,000,000-byte live-memory limit and the local model cost. Cancelling at any step changes nothing, and an unchanged rerun is a no-op. First setup preselects local semantic search (term-only is the alternative); later runs preselect the current mode, and the model is installed and verified only after confirmation and before anything is committed, so a failed setup keeps the previous choices. Term-only turns Memory-Plus off without deleting vectors or the runtime. Settings are written in one atomic config replacement and consent, including the vector cleanup for paused roots, commits last in one transaction, so any failure before that commit leaves settings, consent and stored vectors as they were. A stale preview or changed project directory is refused. A journal beside `config.json` (never inside the database, so backups cannot carry it) marks an apply in progress: overlapping runs, `elepha config`, Memory-Plus toggles, `elepha consent grant/revoke/prune` and `elepha restore` refuse while it exists, and the next `elepha init` finishes or undoes an interrupted apply without overwriting decisions made since, and backfills only roots that are still the exact directory you confirmed. Backfill and capture-service failures after the commit keep the confirmed choices and are reported as retryable gaps, including transcript stores or files the backfill could not list, read or parse and malformed records skipped inside otherwise readable transcripts. `elepha consent` no longer changes search mode, and `elepha consent grant` discloses the same capture and retention contract before granting.
